# CLAUDE_HANDOFF — 月次投入ゲート仕様(ドラフト・発効はバッチ改版時)

クラウド側裁定者より。オーナー承認済み(2026-07-08)。個別株への**月次新規投入額の上限**を
段階制にし、判断記録の実績で解錠する仕組みを discipline-auditor に追加する。
**実装着手はバッチ改版での正式発効後**(判断記録レーン J1-J3 と同じ回で実装するのが自然)。

## 0. 目的
入金力が大きいオーナーにとって、最大のリスクは「待機資金の使いたい圧力」による
検証前の大口投入(飛びつきの資金版)。上限を機械化し、**解錠の鍵を判断記録の実績に紐づける**。

## 1. config(金額は Mac ローカルの config にのみ置く。公開文書・報告に金額を書かない)
- `deployment.monthly_cap_stage`: 現在の段階(0,1,2,…)。**手動でのみ変更**(下記§3)。
- `deployment.stage_caps`: 段階ごとの月次新規投入上限額の配列(**値はオーナーがMacで直接記入**)。
- `deployment.swing_budget_unlocked`: false 固定(事前登録setupが紙上30回を通過した時のみ
  オーナー宣言で true。スイング用の別枠上限も同様に config で)。

## 2. discipline-auditor(radar check)への統合
- 新チェック: 当月の新規買い合計 + 今回の買い候補額が `stage_caps[monthly_cap_stage]` を
  超える場合、**既存の集中度上限(2.5%/5%/10%)と同格の停止判定**を出す。
- 当月投入額の算出元: 判断ログ/取引記録(実装は司令塔設計。記録が無い買いは
  そもそも正規経路外なので check 対象外である旨を明記)。
- 表示は「上限超過」の事実と残枠のみ。金額は端末ローカル表示に留め、Discord・報告への
  出力は「残枠あり/なし」の二値にする(実額の非表示)。

## 3. 段階昇格・降格のプロトコル
- **昇格**: 判断記録の月次レビュー(裁定者作成)が3回貯まり、TOPIX比採点がプラス傾向
  であることを裁定者が確認 → オーナーが宣言して stage を+1(機械は自動昇格しない)。
- **降格**: 月次レビューで規律違反(正規経路外の買い・記録なし取引)が検出された場合、
  または累積-10R相当のドローダウンで、stage を1つ戻す(オーナー宣言・理由を記録)。
- 昇格・降格の宣言は decision_log に append(原則2: 規律の変更は理由つきで記録)。

## 4. テスト要件(合成)
- 上限内の買い候補 → 従来どおり通過 / 上限超過 → 停止判定
- 月替わりでカウンタがリセットされる / stage 変更が反映される
- 出力に実額が含まれない(redaction テスト)
- 既存 radar check の全テスト回帰なし

## 5. 禁止
- stage の自動昇格(実績判定は人間+裁定者。機械は執行のみ)
- 上限の一時的な手動バイパス機能を作らない(緊急時はオーナーが config を変えて
  理由を記録する。こっそり通す裏口を実装しない)
- 金額を公開リポ・報告・Discord に出力しない

規律不変: 売買推奨なし / discipline-auditor を通す前の買いは存在しない / append-only。
発効条件: バッチ改版で INDEX 登録・判断記録レーンと同時に実装指示。
