## §1 受付区分(依頼の種類 × 経路)

| 区分 | 内容 | このセッションへの直接依頼(外出時・チャット) | 拘束力の条件 |
|---|---|---|---|
| **A. 照会** | 状態確認・キューの中身・過去裁定の趣旨説明 | ✅ 無条件で可 | 拘束力なし(回答は ADJUDICATOR_STATE と台帳に基づく) |
| **B. 起案** | ドラフト作成・意見・レビュー・キュー登録 | ✅ 無条件で可 | 拘束力なし(台帳に登録・発効は別途) |
| **C. 正規裁定** | SPEC 発行・受理/差戻し・解除・正本改版 | ✅ **可 — ただし入力実体が GitHub から fetch でき sha256 照合が成立する場合のみ** | 照合成立+裁定文書の発行(URL+sha256 で返す) |
| **D. 入力未達の裁定** | 実体が Mac にのみある案件 | ⚠️ **受付のみ** → PENDING_DELIVERY 二段裁定(第1段=確定済み事実の範囲・第2段=配送照合後) | 第2段で完成 |
| **E. 緊急停止系** | レーン停止・隔離・VOID 指示 | ✅ 確定済み事実の範囲で即時裁定可 | 停止は fail-closed 側なので照合前でも可。**解除は必ず C**(照合必須) |

**禁止線は一本だけ**: 未照合の口頭情報**のみ**を根拠に、拘束力ある**解除・受理・GO** を出さないこと(停止側は可・解除側は不可、の非対称が本質)。

## §2 外出時の実用手順(オーナー向け)
1. **依頼**: このページに短文で可(区分を書く必要はない — 裁定者が §1 で自動分類し、C に足りない場合は D として受け付けて不足物を1行で返す)。
2. **状態確認**: GitHub モバイルで `radar-ops/ADJUDICATOR_STATE.md`(branch `claude/radar-batch-revision-lk9h56`)を開く。ターミナルなら:
   ```
   git fetch origin claude/radar-batch-revision-lk9h56
   git show origin/claude/radar-batch-revision-lk9h56:ai-business-radar/radar-ops/ADJUDICATOR_STATE.md
   ```
3. **裁定回答の受領**: C/D の回答は常に**裁定文書の URL+sha256**(既運用どおり)。チャット本文は要約であり正本ではない。

## §3 状態管理の三層(ターミナル管理の実体)
| 層 | ファイル | 性質 |
|---|---|---|
| ダッシュボード | `ADJUDICATOR_STATE.md` | 3分で読む現在地。毎便更新・上書き可・**sha 照合対象外**(再生成可能なビュー) |
| 台帳(正本) | `BATCH_REVISION_QUEUE.md` | append-only の完全記録(Q1〜)。裁定者の記憶の実体 |
| 裁定文書(正本) | `reports/CLAUDE_HANDOFF_*` | 個別裁定の全文+sha256 |
- 齟齬時の優先: **裁定文書 > 台帳 > ダッシュボード**(ビューは常に負ける)。

## §4 単一裁定者原則
1. 裁定権を持つ裁定者セッションは**常に1つ**(現在=本クラウドセッション)。ターミナル等での併走起動は行わない(二重司令塔・二重採点の実害と同型の事故を防ぐ)。
2. 将来ターミナル(Mac の Claude Code CLI)へ移す場合の**移管手順**:
   (i) 現裁定者が「移管宣言」文書を発行(未完キューの snapshot+INDEX/STATE の最新 sha を同梱)
   (ii) 新セッションが starter 06+本 PROTOCOL+STATE で起動し、照合結果を発行
   (iii) 現セッションはオーナーが閉鎖(**閉鎖の確認をもって移管完了** — 両生存期間を作らない)。
3. セッションの世代交代(同じクラウド内での引き継ぎ)は移管ではなく、starter 06+台帳による通常の再構成で行う。

## §5 用語の整理
- 本体制での正式呼称は**裁定者(cloud adjudicator)**。オーナーが「選定者」と呼ぶ場合も同一役割を指すものとして扱う。ただし**銘柄・タスクの「選定」は裁定者の役割に含まれない**(検証優先度の裁定はするが、投資対象の選定・推奨は R2 により誰の役割でもない)。「選定」を新役割として設ける場合は別途の統治裁定を要する。
