# 開発ワークフロー — 原則から実装まで(サブエージェント分業)

このプロジェクトは「人間が**原則と契約**を握り、**計画・コーディング・検証**はサブエージェントに
委ねる」Nakajima流で進める。人間の丁寧な仕事は前半(Phase 0〜1)に前倒しされ、
後半のコーディングは "原則の自動的な帰結" になる。

## 役割分担の原則
- **人間が握る**:設計原則(`DESIGN_PRINCIPLES.md`)、インターフェイス、データ構造。最終承認。
- **委ねる**:仕様の起草補助、実装プラン、コーディング(99%)、検証。
- **レビューの仕方**:コードを行単位で読むのではなく、**「原則に忠実か」だけ**をゲートで見る。

## サブエージェント(`.claude/agents/`)
すべてのエージェントは**着手前に `DESIGN_PRINCIPLES.md` を読む**。原則に反する作業はしない。

| エージェント | 役割 | 入力 → 出力 | 主に守る原則 |
|---|---|---|---|
| **spec-architect** | 契約(IF・データ構造)を起草 | 原則 → `SPEC.md` | 6(ファイル/宣言), 2/3/5の契約化 |
| **planner** | 実装プランを作る(コードは書かない) | 原則+SPEC → `PLAN.md` | 全原則の計画反映 |
| **implementer** | プラン通りにコーディング(99%) | PLAN+SPEC → コード | 6(未来を見ない/宣言的) |
| **principle-auditor** | 原則準拠だけを監査(憲法裁判所) | 成果物 → 原則別の判定 | 1〜6 全部 |
| **verifier** | 実際に動かして挙動と再現性を確認 | コード → 実行結果・テスト | 3(鮮度), 5(閉ループ), 6(再現性) |

## フロー(各フェーズは「principle-auditor + 人間」の二重ゲート)

```
Phase 0  原則確定  …… DESIGN_PRINCIPLES.md(人間が著者)         ← 完了
   ↓
Phase 1  契約定義  …… spec-architect が SPEC.md を起草
   └─[人間ゲート] インターフェイス/データ構造を承認     ← ここが最重要の人間仕事
   ↓
Phase 2  計画      …… planner が PLAN.md を作成
   └─[auditor] プランは原則に忠実か → [人間ゲート] 承認
   ↓
Phase 3  実装      …… implementer がコーディング(99%委任)
   └─[auditor] 原則違反は無いか + [verifier] 実際に動くか → [人間ゲート]
   ↓
Phase 4  検証運用  …… 閉ループ(判断→結果→学び)で原則自体も磨く
```

## 原則 → 守護者(誰がどの肝を見張るか)

| 原則 | 主な守護者 | 実装での確認観点 |
|---|---|---|
| 1 最終判断は人間 | principle-auditor | 自動執行が無い / ツールは読みを出すが決めない |
| 2 規律を破るなら記録 | spec-architect, auditor | 上書きを記録する仕組み(decision/override log)が契約にある |
| 3 無知が最大の罪 | spec-architect, verifier | データ鮮度/欠損/遅延の表示が必須、不確実性を先頭に出す |
| 4 参謀であって事務員でない | auditor | 出力に読み+根拠+反証が並置される |
| 5 検証するための道具 | verifier | 判断→結果→学びの閉ループが機能する |
| 6 ファイル/宣言/未来を見ない | auditor, verifier | look-ahead無し・宣言的config・二度実行で同一出力 |

## SPEC が必ずカバーすべき「原則が要求する構成要素」
spec-architect は以下を契約として定義する(原則からの導出):
- **decision/override log**(原則2):規律と異なる判断をしたら、理由を構造化して残す。
- **freshness/quality gate**(原則3):全レポート冒頭に asof日・遅延・欠損を明示。古ければ大きく警告。
- **uncertainty-first 表示**(原則3):「何が分かっていないか」を先頭セクションに。
- **両面プレゼンタ**(原則4):仮説には必ず反証・弱気シナリオを対で出す。
- **feedback loop / journal-review**(原則5):裁量の上書きが規律ベースラインを上回ったかを集計。
- **honest backtest**(原則6):ポイントインタイム・ユニバース・正直なコスト。自選銘柄BTは禁止。
- **宣言的config**(原則6):戦略・方針・パラメータはデータ。エンジンはそれを解釈する薄い汎用層。

## 起動例(Claude Code)
```
# 1) 契約を起草させる
> spec-architect サブエージェントで SPEC.md を起草して。原則に厳密に従うこと。
# 2) 人間が SPEC を承認したら計画
> planner サブエージェントで PLAN.md を作って。
# 3) 監査
> principle-auditor で SPEC と PLAN を原則別に監査して。
# 4) 実装 → 監査 → 検証 を回す
```
